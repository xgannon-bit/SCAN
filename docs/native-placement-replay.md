# Reviewed native placement experiments

Repair Review can construct an exact placement ROI X, Y, or coupled X/Y edit from
the selected native record. This is a copy-only qualification operation. It does
not infer the physical correction, qualify an Eagle build, or repair dependent
inspection behavior. CAD, stored centers, Masters, local windows, algorithms,
bindings, FOV membership, enable flags and unknown fields are preserved.

## Replay and diagnosis

Historical replay records what changed between separately identified archives.
Its evidence has `kind: historical-replay` and `independentSupport: false`.
Reproducing the target literals demonstrates the writer and review workflow; the
target archive is not independent proof of the right physical location. The
evidence digest binds the explanation and file hashes to each exact proposal.

The separate `independent-source-support` option records a reviewer's declared
source evidence. The writer checks identity and preservation, not the truth of
that engineering explanation. Neither mode silently becomes an automatic repair
recommendation. A source residual, body origin, model anchor, and misplaced local
window are different observations; a numeric match alone cannot select a repair.

## Transaction and adapter boundary

The source archive, selected main XML and explicitly selected main Master hashes
must match. Guarded edits require a uniquely resolved plain module ID and Master
key, and matching main/Master schema claims. Temporary or backup Masters, missing
selection, and attributed or nested identity ambiguities remain held. These
checks establish the literal affected scope, not runtime coordinate semantics.
Each proposal binds
module (`ParentId`), reference (`RefID`), native Part ID and Master key. An ordinal
path is a locator hint and never the target identity by itself. A coupled X/Y
operation uses mutually required proposals so a partial accepted pair is refused.
The ROI guard records the exact original X, Y, width, height and angle; stale
guards, ambiguous identities, unsupported schemas and incompatible operations
refuse writing.

The observed 10.2 route retains its existing scalar operations. The narrower 10.1
experimental path is restricted to ROI X/Y and requires the complete ROI guard.
The schema claim is not the Eagle executable version. Actual-source fixture
qualification and machine qualification are separately reported in each private
delivery; synthetic coverage is never reported as an actual archived-job run.
Preparation constructors remain subject to their existing independent adapter
gates; read support for a schema does not enable native construction for it.

Edits replace exact scalar byte spans. Removing those changes must recover the
original bytes. The complete candidate preserves all other archive payloads,
including distinct Temp/backup states. It does not rewrite save timestamps to
imply a later machine save. Existing enabled states remain as supplied; they do
not confer inspection readiness and do not enable newly prepared drafts.

Repeated export starts from the unchanged original and applies absolute target
values. It never adds a displacement to a previous output. Passing a changed
archive to an old request is a stale-source refusal, not another movement.

## Operator workflow

1. Import the complete copied job and explicitly select its main and Master.
2. In Repair Review, select the full component identity, operation and exact
   proposed literals. Choose historical replay or declared source support, attach
   the evidence, and explain coordinate/dependency limits.
3. Check the proposal, inspect original/proposed geometry and the affected scope,
   then accept or reject the exact operation. Returning to pending undoes approval.
4. Acknowledge qualification-only output and export the complete separate job.
5. Review the reparsed candidate and remaining work. Save/reopen the project to
   recheck the original and candidate bytes, source-bound decisions and history.

Repair-only reanalysis does not require a PCB, Gerber or preparation constructor.
It replays the accepted transaction against original bytes to check the exact
candidate main hash and compares every protected companion payload. Native
dependency observations and machine work remain visible even when placement
literals match the requested result.

## FOV and binding

Saved FOV assignment and verified acquisition coverage are separate states.
Empty, assigned, ambiguous and unresolved literal relationships can be reported;
an assigned ID does not show that the body and all dependent search/inspection
windows fit inside usable camera coverage. Camera-center proximity alone cannot
qualify a native FOV writer. Coverage, calibration, optical access, image channels,
height acquisition and native binding semantics remain held without evidence.

## Qualification after offline checks

Use the established local Eagle procedure to compare an untouched control and
the separate candidate. Record the executable build, conversion/sync prompts,
selected snapshot, changed component identities, geometry before/after saving,
binding/FOV behavior and dependent window positions. Keep complete saved copies.
Opening successfully does not demonstrate fresh optical inspection or defect
sensitivity. Each machine needs its own evidence; RCP retains release authority.
